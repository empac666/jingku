# Jingku 1.0.2 startup crash fix — local only

The reported “won’t open” is not yet confirmed as a crash rather than an installation failure. This release fixes a concrete early-startup defect found in source, adds defensive initialization and local crash diagnostics, and preserves the existing signing identity. It has not been run on the reporting phone.

## Ranked likely causes and evidence

Source paths below are relative to `app/app/src/main/` unless prefixed otherwise. Old source refers to the 1.0.1 mirror commit `3348d5d347285d4f1409e073dd1b0fe39f2f49c7`.

1. **Early locale initialization dereferences a potentially null application context. Highest-confidence source defect; likely explanation if installation succeeds and the app immediately exits.** Old `java/com/broll/poc/BrollApplication.kt:12` calls `LocaleStore.wrap(base)` during `Application.attachBaseContext`, before application creation completes. Old `LocaleStore.kt:15` calls `context.applicationContext.getSharedPreferences(...)` without a null fallback. At that lifecycle point the application context can be null. Evidence snapshots: `evidence/crashfix-1.0.2/old-BrollApplication.txt` and `old-LocaleStore.txt`. Fixed in `LocaleStore.kt:15` using `(context.applicationContext ?: context)`. Application locale failure now yields an in-app startup error. A real-device trace is still needed to attribute the user's failure conclusively.
2. **Installation incompatibility, if “won’t open” actually means “won’t install.”** The 1.0.1 `aapt2 dump badging` output reports minSdk 26, target 35, versionCode 2 and only `arm64-v8a`. A phone running Android below 8.0, or a 32-bit-only Android OS even on a 64-bit CPU, cannot install this APK. An already installed build with a higher versionCode prevents normal downgrade; a different signing certificate prevents replacement even when the versionCode increases. `old-badging.txt`, `old-manifest.txt` and `old-signature.txt` are direct tool evidence. 1.0.2 is code 3, arm64-only, minSdk 26; same certificate as 1.0.1. ABI/OS restrictions remain intentional. Obtain the actual installer error before diagnosing this case. No `testOnly` or debuggable flag appears in the merged release manifest.
3. **Storage/device-probe exceptions or main-thread work at startup. Plausible secondary failures, without a phone trace.** Old `MainActivity.kt:123-131` synchronously opens bundled SQLite, constructs `MetricsLogger` and ensures model directories; old `MainActivity.kt:168` verifies model files. Old `metrics/MetricsLogger.kt:122` writes CSV headers without protection, and `log()` probes battery/thermal APIs and appends files without protection. External storage unavailability/disk errors or vendor probe exceptions could abort activity creation. Model SHA verification on the main thread can stall a launch with large existing weights. Current `MainActivity.kt:104` guards UI initialization, `:182` opens/counts the DB on IO, `:606` verifies model status on IO. Current `MetricsLogger.kt:122`, `:235`, `:275` treat header/probe/append failure as nonfatal. Directory or layout failures use a plain-widget error screen with copy/share details. No network download is started at launch; model downloads require a user action.
4. **Bundled SQLite/native loading, reflection, theme/layout and manifest problems were investigated; no packaging defect established.** Details follow. Java/linkage failures are handled or captured; native process signals still require logcat/tombstones.

## Crash diagnostics and behavior

`CrashGuard.kt:8` installs `Thread.setDefaultUncaughtExceptionHandler` at the first statement of Application.attachBaseContext, before locale setup or other application initialization. The handler formats model/manufacturer, Android release/API, supported ABIs, app name/version code, timestamp, thread and full nested stack trace. `CrashReport.kt:15` creates `filesDir/crash`, writes UTF-8 `last_crash.txt`, flushes/fsyncs and closes the file. Reporting errors never replace the original exception; the previous Android handler is invoked in finally.

On the next launch, `MainActivity.kt:231` shows the saved trace with Chinese/English **Copy**, **Share** (`ACTION_SEND`, text/plain), and **Dismiss and delete**. Copy/share retain the report on disk; explicit dismissal deletes it. Handled startup failures show details immediately through the same copy/share UI. Partial widget initialization is safe during state saving/destruction. Initialization coroutines are cancelled when the fallback UI is shown; a database opened during a cancelled launch is closed.

The guard covers uncaught Java/Kotlin exceptions, including managed linkage errors; it does not catch native SIGSEGV/abort, ANRs, OS kills or installation errors. Persistence is best effort if app storage is unavailable/full. No report is uploaded automatically. Device-only UI behavior (actual clipboard/share chooser/dismiss and crash-relaunch) still needs manual verification.

`CrashReportTest.kt` adds three tests: metadata and nested trace formatting plus UTF-8 directory/write/overwrite; chaining the original exception despite a disk-writer failure; writing before chaining. Existing 24 tests remain.

## Information to request from the phone user

- Phone manufacturer/model and Android version; whether the APK installs successfully or fails before opening. If installation fails, send the full installer error text and whether another Jingku version is already installed.
- Install the signed 1.0.2 APK as an update where compatible. If a crash dialog appears, use Copy or Share and send its complete text (app sends nothing automatically).
- If it still closes without a dialog, capture `adb logcat -b crash -d` immediately after reproducing, plus any native crash/tombstone details available. A native crash or OS kill may not create a Java crash report.
- Useful device/install diagnostics: `adb shell getprop ro.product.model`, `adb shell getprop ro.build.version.release`, `adb shell getprop ro.product.cpu.abilist`, and the full output of `adb install -r jingku-1.0.2-arm64-v8a.apk`. Do not uninstall first: uninstalling deletes local indices/preferences and is not needed for a correctly signed update.
